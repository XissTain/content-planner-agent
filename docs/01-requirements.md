# 01 · 需求与选题

## 为什么选第 2 题

依据当前试卷的三小时建议、模型动态决策和可验证交付要求评估，未假设候选人有未提供的项目经验。

| 题目 | 优势 | 核心难点 | 本次判断 |
|---|---|---|---|
| 1 素材审核与排期 | 风险、冲突、幂等均可验证 | 审核、时段、用户确认和保存边界同时存在 | 可做，但业务边界较多 |
| 2 内容任务规划 | 成本和耗时可计算，重规划与恢复易观察 | 真实决策、状态依赖、失败不能伪报成功 | 最适合本次交付 |
| 3 企业知识问答 | 文档检索和引用易上手 | 冲突查证、上下文、引用支撑需逐项验证 | 可做，但事实评估更费时 |
| 4 短视频脚本 | 与题面中的内容业务贴近 | 脚本事实、时长修正、质量都需验证 | 可做，但创作质量增加验收变量 |

## 用户、输入和产出

用户是需要在预算和截止时间内准备内容活动的运营人员。

必填：请求 ID、主题、预算、截止时间。可选：必需素材、初始服务偏好、模拟起始时间。

候选人在优化阶段确认的业务规则：预算不足时优先保留创意脚本，先简化制作。以可选 replan_priority 字段表达；质量偏好不能覆盖预算和截止时间。相反偏好作为对照用例验证需求变化确实能影响方案。

产出：活动任务计划、依赖与耗时、业务步骤实际状态、每次工具结果、方案费用合计、保存状态；无法完成时说明缺信息、约束缺口或工具问题，并保留已有结果。

## 范围

使用 CLI、合成素材、本地工具和 SQLite。真实模型通过 Codex CLI 接入；离线 Mock 独立标记。交付的是方案，不执行付费制作或实际发布。无需 UI、线上部署、多 Agent 或生产 Runtime。

## 成功标准

1. 正常完成：保存的计划费用等于逐项加总，完成时间不晚于 deadline。
2. 缺预算或截止时间：返回 `needs_input`，不自行补值，不调用业务工具。
3. 工具失败：记录真实失败；由模型决定重试、改选或结束；成功步骤不丢失。
4. 预算超限：模型看到不通过的测算后调整组合、重新测算；没有可行方案则返回 `incomplete`。
5. 重复执行：同一请求只有一份方案；相同 ID 更改输入须拒绝。
6. 加分项续跑：进程重新启动后可从数据库读取成功步骤，继续失败步骤。
7. 调用有上限；达到上限明确未完成。`completed` 以真实数据库保存为必要条件。
8. 提供至少三组输入、实际输出与 Trace；至少两条真实模型路径体现工具结果改变下一动作。

## 人与 AI 的分工

Codex 辅助需求分析、实现、测试与文档。候选人确认业务假设、亲自复跑、理解并修改关键代码，记录自己的实际贡献和用时。个人尚未进行的工作必须写为待完成。
