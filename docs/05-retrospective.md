# 05 · 工程复盘

以下记录本次实际发现和修复的问题。它们由 AI 辅助排查，候选人个人学习心得须理解并实际参与后补充。

## 方案可行不等于实际完成

模型说“已保存”不能替代数据库写入。保存依赖已成功脚本和通过校验的测算，finish 不接受 completed，真实数据库写入异常也必须返回失败。测试通过 SQLite 触发器拒绝写入，验证失败不会伪报成功；解除故障后只续跑保存。

## 历史成功不能掩盖最新失败

原先只要某个工具曾成功，汇总步骤就可能继续显示成功，即使它的最新一次调用已经失败。修复为展示最新调用状态，并单独保留历史成功次数和成果。失败原始记录不可改写。

## 续跑需要跨越真实进程边界

原先工程测试支持重开数据库，但样例评估的续跑仍在同一个 Agent 实例中完成，证据力度不足。新版验收分别启动两个 CLI 进程，检查 PID 不同、首次保存失败、脚本 ID 不变，以及第二次只有 save_plan 一个动作。

同时修复离线替身的重试累计问题：上次达到两次失败上限后，新的运行应重新拥有有限重试机会，而非永久停止。

## 真实时钟不能被冻结

固定模拟 start_at 便于复现；真实请求没有 start_at 时，续跑和模型等待都会消耗现实时间。旧实现沿用首次时间，可能错误地保存已经过期的计划。现在在每步前刷新测算，并在生成和保存前再次校验。测试分别覆盖续跑时过期与模型返回动作前过期。

## 状态相同也可能是假阳性

旧评估中，只要最终 incomplete 就可能把“预算不可行”场景判通过，未排除模型超时。新版加入 no_unexpected_model_failure，并要求不可行场景有工具测算和模型业务停止。检查结果需要支撑需求本身，不能只匹配一个状态字符串。

## 模型调用环境与失败保留

初次接入遇到网络/代理问题；扩展验收又出现多次超时。隔离试验同时调整桌面环境继承和用户配置读取后，同一份观察输入返回了正确动作。正式接入据此收紧为独立 CLI 上下文，显式指定目标模型、保留账号登录能力并关闭无关工具，再执行新版验证。

没有进行完整单因素因果分析，因此不把某个环境变量断言为唯一根因。旧失败记录保留在 verified-v2，不能删除后声称从未失败。小样本修复后通过也不代表服务具有 100% 可用性。

## 业务优先级要影响实际方案

候选人选择保留创意脚本后，预算 10 的合理目标是保留 premium、把制作改为 simple，合计 10；对照的保留制作偏好则应更换脚本。最便宜不是自动等于最符合需求。程序守住硬约束，模型在允许范围内根据偏好选择路线。

## 下一步

当前是本地串行原型，业务工具和资料为合成实现。进一步工程化可增加并发请求锁、真实付费工具预算账本、服务超时分类和更大规模多次模型评估。这些不作为已经完成的能力，也不为了框架名称增加本题不需要的复杂度。
